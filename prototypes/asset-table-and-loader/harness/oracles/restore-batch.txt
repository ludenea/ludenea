# Oracles of the family "restore-batch": the answers to a restore complete
# the batch of each closure.
# Written by hand from the design text, by a writer who has not read the build.
# The table's order is the order of the asset identifiers:
# D, F, G, N, P, Q, U, X, Z. Every asset is of the first type.
# Record lines stand in the order applied: the commands first, in the order
# the scenario gives them, then the arrivals by asset identifier.
# An entry line with no want line under it is an entry that holds no want.
# Where the text left a choice, a comment says which reading the lines take.

scenario restore-batch/saved-world

# The table the creation gives: the two wants of the composition. The world
# is gated on P and Q before its first tick, and the scripted batch opens the
# gate, a failed arrival being an answer.

entry Q parameters unavailable
want contributor:base required

# required as the parent's want is; then the arrivals, by identifier. G fails

# The readers of the save, each under the content at hand, into the saved
# world's composition, naming no set. Before its first tick a reader waits
# for a marked answer to every asset its table holds available, under a want
# or under none: D, P, Q and Z. The save holds no unanswered want.
# Reading taken, as in the family "restore": the step without waiting, before
# the answers are posted, names every entry that awaits its marked answer, in
# identifier order.
# The batch. The capability follows the closure of each answer in the
# manifest at hand and posts with the answers, as an ordinary arrival,
# unmarked and with its event, each asset that a want the core adds from a
# part at hand creates or returns to unavailable, and an entry the save holds
# unavailable under no want that such a part lists. An entry the save holds
# as failed under a want that stands, on which the parts at hand add no want,
# receives nothing. An ordinary arrival is no answer: the event of the
# restore does not name its asset.
# N, U and Z lost their last want during tick 8: each falls once the record of
# tick 9 is applied, unless a want names it by then.

scenario restore-batch/recorded-hashes
restore continues
blocked 9 awaiting D, P, Q, Z

# Every answer is at the recorded hash and the save holds no unanswered want:
# the saved run continues. No event on a marked answer, none for the restore.
# The parts at hand are the recorded ones: P lists D and Q lists G, and each
# want the core added for them stands, so no want is added and no entry is
# returned to unavailable. The three failed entries receive nothing, although
# their artifacts are whole: G, the failed dependency of a parent answered at
# its recorded hash, F under the host's want, and N under no want. U receives
# nothing either: no want names it and no part lists it.
# The answer of Z is for an entry no want names: it changes nothing. N, U and
# Z fall. The table is the saved world's of tick 9.
