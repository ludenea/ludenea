# Test recording round trip

Throwaway spike of the game testing research, never product code. A failed test should leave one file from which anyone, on any machine of the compatibility boundary, replays the failure. This spike measures, instead of assuming, whether such a file written on one cell is read and replayed on every other; whether a tool lists and checks it from the description the file carries, without a world; whether a changed or a cut file is found, and where; whether a test report assembled from the start markers and the records that the tests write is complete and exact when the test process is ended from outside; and what an invariant read after every tick costs.

## Layout

- `src/world.rs`: the world, a copy of the [persistent pool prototype](../workload-persistent-pool/README.md)'s (the [reference workload](../reference-workload/README.md) on the dependency-counting tick graph, a job that an executor runs, stepped by whole ticks, snapshot and restore into a new world), with three additions. Every tick takes an input record, an ordered list of velocity kicks validated against the state at the tick boundary and applied in the repulsion pass, as the [control surface toy](../control-surface-toy/README.md) does. The state hash is computed at a cadence (every tick, or every sixtieth). The state at the current tick boundary is readable between steps. A sequential oracle steps the same records with the reference crate's systems.
- `src/pool.rs`: the two pool kinds of the persistent pool prototype, copied unchanged without their self-checks.
- `src/container.rs`: the container and its client. A file is a header (a magic, the container's version, the file's length, a table of sections with their offsets, lengths and digests, and a digest of the table), then the sections. The first section is a description of record types in a small type system (unsigned integers of 8, 32 and 64 bits, a 32-bit float, a text, bytes, a sequence of records of a named type); every other section is a run of records of one described type. This module knows nothing of the world or of what a recording means: it lists, checks and reads a file with the description the file carries. Every length is checked against the bytes that remain before anything is allocated, and a type may only contain types declared before it.
- `src/recording.rs`: a recording of one world and its replay. The header holds the workload version, the snapshot format, the world's creation values, the starting tick, the hash of the starting state, the last tick, the test's name and the writer's cell and profile. The starting state comes in one of two forms: the self-contained form carries the snapshot; the reference form carries the recipe instead (the creation values and the input records of the fixture's preparation) and no state. Then the input record of every tick (its tick, its source's identity, its kicks) and the hash of every tick. A replay checks the header against the build, restores or rebuilds the starting state, compares its hash with the recorded one before any record of the run is applied, checks each record's tick against the one before, steps every record in one multi-tick step, and compares the recorded hashes with the replayed ones. Its verdicts: verified, diverged at a tick, replayed with nothing compared, refused.
- `src/run.rs`: the run's directory and the assembly. A test passes its name and its body to an entry function, which writes a start marker before the body runs, runs the body, writes the record whole under another name, puts it in place by one rename and removes the marker. The assembly is an ordered list of rules over the harness's listing and the directory: a completed record gives its outcome; a marker and no record is an interrupted test; neither is a test not run when the process was lost, an unknown outcome when it failed, a pass without a record when it succeeded. The rules on ignored tests and on a process ended by the runner's own time bound are not built.
- `src/lib.rs`: the fixture as a recipe (a world of the default seed, then sixty ticks of scripted kicks) whose snapshot is its cache, the scripted session that steps a world one tick per call and keeps its input log, and the invariant the failing test reads after every tick.
- `tests/suite.rs`: sixteen tests of the standard harness on the small size, sharing one runtime instance with a persistent pool of 4 workers. Fifteen restore the fixture and step 120 ticks, one tick per call. One watches the sixteen first live entities and fails when more than eight of their handles have gone stale, which the workload's kills bring about at a tick the seed decides; it leaves its recording in both forms. Outside a run of the orchestrator that test checks that the invariant fails and passes, so that the workspace's tests pass.
- `src/main.rs`: the orchestrator and the report, one JSON document on standard output.
- `recordings/`: the recordings that the failing test wrote on each cell of the research CI, carried here from a first run's artifacts so that every later run reads the files of the other cells.

## Hypotheses

With the reference workload, version 1, wander system off, compiled by the pinned Rust toolchain at default target features, in release and unoptimized builds:

1. **A recording is portable as a file.** The failing test leaves a single-file recording in each form; another process replays it to the failing tick with every recorded hash equal to the replayed one, at 1 and at 4 workers, on each of the five cells, whichever cell wrote the file. The sections that hold no writer's name (the snapshot, the preparation, the inputs, the hashes) are byte-identical across cells. Refuted by one differing hash, or by one file a foreign cell cannot read.
2. **The reference form is checked.** The reference form with one input record of its recipe's preparation changed in the file, which no field of the header holds, is refused when the rebuilt starting state's hash differs from the recorded one, before any record of the run is applied. Refuted by a replay that applies a record of the run after a differing starting hash.
3. **The container is read from its description, and a damaged one is found.** A client that knows the container and the description's format, and nothing of the recording, lists every file with its sections, their record types, counts, sizes and digests. A recording with one byte of one input record changed is reported: by the container's integrity when the byte is changed in place, and by the replay at the tick of the changed record, the first divergent tick, when the file is made whole again around the change. A cut file is refused before any step. Refuted by a file the client cannot list, a change not reported at its first divergent tick, or a cut file not refused before any step.
4. **The assembly is complete and exact.** Sixteen tests at a harness parallelism of 4 each write a marker and a record, and the assembly lists every test once with its outcome. With the process ended from outside while four tests are started and unfinished, eight finished and four never started, the assembly names the eight with their outcomes, the four started ones interrupted and the four others not run; a resumed run of the interrupted and not run tests completes the report, equal in outcomes and final hashes to the uninterrupted run's. Refuted by a test missing from, doubled in or wrongly classed in a report.
5. **The cost of a per-tick invariant** is measured without a threshold: an invariant over a query of the 10 000 entities read after each one-tick step, at a hash cadence of 1 and of 60, against the same ticks in one multi-tick step, at 1 and 4 workers.

## Method

The orchestrator builds the test target with the child `cargo` in its own target directory, reads the executable's path in the build tool's messages and the tests' names in the harness's terse listing, then does the rest as a process that never ran a test.

**The whole run.** The suite runs with 4 test threads and a fresh run directory. The report is assembled from the listing and the directory, and compared with two witnesses that do not read the directory: the harness's own verdict per test on standard output, and one line per test that the entry function writes on standard error when the test finishes.

**The run ended from outside.** The suite runs again with an environment variable that makes the entry function hold every test that starts after eight have started: such a test has written its marker, says on standard error that it holds, and waits. With 4 test threads the harness starts the tests in name order and a thread holds only after it has finished its earlier tests, so when four tests hold, eight have finished and four have never started, by construction and not by timing. The orchestrator reads standard error, ends the process when the fourth test says it holds, and assembles. The classes are compared with what the tests said: finished, held, or nothing. The orchestrator then runs the interrupted and not run tests by exact name in the same directory and assembles again.

**The recordings.** The two files the failing test left are copied to the output directory, so that the run's artifact carries them. Each is listed by the description-driven client and replayed at 1 and 4 workers on a persistent pool. So is every file under `recordings/`, which holds the two files that each cell of the research CI wrote in an earlier run: a cell therefore replays the files of the four other cells and of an earlier run of its own. The same failing run is also made at the measured size (10 000 entities) by the orchestrator itself, recorded in both forms, listed and replayed, and its sections' digests are compared across cells; that file is written and read by one process.

**Changed and cut files.** On the two files of the run: one byte in the middle of the inputs section is changed in place; the sign of one kick of the middle input record is changed and the file encoded again, whole, with the count of bytes that differ from the original; in the reference form each of the sixty preparation records in turn has the sign of its first kick changed, the file whole; both files are cut at 0, 7, 20 and 100 bytes, at half their length and one byte short; and the hashes are trimmed away.

**The cost of an invariant.** For each worker count (1, 4) and hash cadence (1, 60), on a persistent pool: after a 10-tick warm-up, 600 ticks in one multi-tick step, 600 one-tick steps, and 600 one-tick steps each followed by an invariant that reads the position and the velocity of every live entity. Wall time per tick, the best of five rounds; the three final states are compared. The invariant alone on a state at rest is timed over 2 000 evaluations. An unoptimized build measures the small size over 120 ticks and three rounds, and the report says which size ran.

**What the spike does not build.** The comparison of hashes runs after the multi-tick step and not inside it. The world of a replay hashes every tick whatever the recording's cadence. A hash outside the cadence keeps its node in the tick graph, which computes nothing: a one-tick step still waits for that node, and the placement of the hash as work pending across steps is not built. Nothing here has physics, so no replay restarts a world. The entry function is this spike's own and holds no engine.

The self-checks (`cargo test -p test-recording-round-trip`) run on the small size: the world with kicks matches the sequential oracle at 1, 2, 3 and 8 workers in batches of 1, 7 and the whole run; a hash cadence of 60 keeps the hashed ticks and their values; a container reads back from its description, every cut and every changed byte of a sample file is refused, a type that contains itself and a count larger than the bytes that remain are refused; both forms round trip through their file and replay verified; a changed run record diverges at its tick and a changed preparation record is refused before any record or leaves the starting state the same; a recording without hashes is never called verified and a gap in the ticks is refused; exactly one rule of the assembly applies to every listed test, a record beside a leftover marker included; and the whole report runs with every check passing.

## Environment

The five cells of the research CI and one local machine, the pinned toolchain, release and unoptimized profiles, default target features. No dependency beyond the reference workload crate.
