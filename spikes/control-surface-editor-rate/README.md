# Control surface at editor rate

Throwaway spike of the control surface research. A paced host steps the [reference workload](../reference-workload/README.md) at 60 ticks per second while a paced editor session observes and edits it: a subscription to coalesced change sets over all 10 000 entities at a 60 Hz period, a live-value subscription over 100 fields, and a scripted drag that sends one `set` command per field per tick on 10 entities for 10 seconds and closes with one transaction whose inverse it asks for. It measures, instead of assuming, what the session costs the stepping thread, how long an edit takes to come back as a live value, how large the messages are, and what a stepped agent session on a second world of the same process loses while the editor session runs.

## Layout

- `src/world.rs`: the world, a trimmed copy of the [control surface toy](../control-surface-toy/README.md) spike's (the reference workload on the dependency-counting tick graph, with the input fixed point). The inputs of a tick are commands of three kinds, resolved against the state at the tick boundary in record order into one input velocity per touched slot: the agent's kick, the editor's `set` of one field, and a transaction of field sets validated whole before any is written, whose inverse (the values the fields held at the boundary) is computed there. The graph owns no threads: a step runs on the calling thread plus the helpers a pool lends it. A sequential oracle steps the reference crate's systems with the same records through the same resolution.
- `src/pool.rs`: a small persistent worker pool shared by the worlds of one process. A stepping world offers one ticket per helper it may use; an idle helper takes the oldest ticket and serves that world until its step ends. The calling thread is always worker 0 of its own step, so a step never waits for a helper. This is coarser than the [persistent pool](../workload-persistent-pool/README.md) spike's design, where a worker claims tasks from any active job.
- `src/host.rs`: the paced host and the server side of the session. The watched component, the extracted state, the stepping thread's loop, and the I/O executor (a second thread with the session's period).
- `src/wire.rs`: the messages. Every stable name is written either as a string or as a session-scoped integer (the interned names capability), and the rows of a state stream either as canonical bytes with the field names once in the header or as name-tagged fields in every row, so that each message is measured in each form.
- `src/transport.rs`: the two transports of a paced session, which is a duplex stream: in process (a channel one way, a direct call the other) and a loopback TCP socket with length-prefixed frames, one reader thread per connection.
- `src/client.rs`: the scripted editor. `src/agent.rs`: the stepped agent of the toy spike's pattern (it observes sixteen entities, kicks them toward the center, steps a batch of ten ticks), through the typed in-process path.
- `src/main.rs`: the scenarios, the verdicts and the report.

## What runs on which thread

- **The stepping thread** sleeps until the tick's deadline, then: takes the commands the session received since the last boundary as the tick's input record (the admission), steps the world one tick, runs the sampling system that writes the watched component, copies the state into the extraction's back buffer (the extraction), computes the tick's change bitset from the component's change ticks, and under one short lock swaps the buffer with the shared one and merges the bitset into the shared pending bitset (the publication). It encodes and sends nothing.
- **The I/O executor** wakes at the same period, half a period after the tick's deadline. It swaps the shared buffer for its own and takes the pending bitset under the same lock, then builds and delivers the change set (the current values of every entity whose bit is set, which coalesces every tick since its last delivery) and the live values (the subscribed fields whose value or entity generation changed since they were last sent). Three buffers rotate between the two threads, so neither waits for the other longer than a swap. The connection's reader thread decodes the client's commands; with the delivering thread it stands for the I/O executor.
- **The editor client** runs on its own thread. At every live-value message whose tick advanced it sends the drag's commands, so at most one command per field per tick; it takes its entities' handles from the live values, so a dragged slot whose entity was replaced is followed.

## Interpretations

The specification of this spike leaves four choices open; each is stated here because the verdicts depend on them.

- **The fraction of entities changing per tick.** The reference workload moves every entity every tick, and its hashes may not change. The watched component is therefore one this spike adds beside the hashed state: `sampled_motion`, the position and velocity of an entity as a time-sliced system last sampled them. At tick `t` the system samples the slots whose index plus `t` is a multiple of a period of 100, 10 or 1 ticks: exactly 1, 10 or 100 percent of the entities change per tick, with values the fixture's systems produced, and the simulation is untouched. The component keeps a change tick per chunk and per entity, as an ECS would.
- **The fields the drag sets** are the two velocity components. The tick graph reads a slot's velocity in one place, so the input stays local; an input on the position would have to reach the spatial hashing and every neighbour's force. The value that comes back in the live-value stream is the velocity after the tick that took the input, not the value sent.
- **What counts as time on behalf of the session.** The hypothesis charges the session with publishing the change bitset and nothing else. The verdict uses the stepping thread's time, measured directly inside the session's run, for the admission and the publication. The extraction is reported beside it and not charged: the same extraction would feed a renderer. Three paced runs give the comparison "with and without": without session and without extraction, with the extraction alone, and with the session.
- **The full-state read** is every component of every slot at one tick boundary (generation, alive flag, position, velocity, mass, the watched component) and the two globals, in the same encoding as the change set it is compared with. A change set row carries the entity's handle (8 bytes) that a full read does not need, so a change set of the whole component set at 100 percent would exceed the full read: the comparison holds for a watched set narrower than the state, here 4 of its 9 values.

The latency of a `set` command runs from the client's write to the client holding the live-value message of the tick that decided the command (the message says through which request the session's commands were decided). The verdict takes the 99th percentile over the commands in milliseconds against two tick periods; the maximum is reported beside it.

## Hypotheses

With the reference workload, version 1, default size (10 000 entities), wander system off, at 1 and 4 workers, the world paced at 60 ticks per second and the session at a 60 Hz period:

1. **The stepping thread's share.** The stepping thread's time on behalf of the session (admitting its commands, publishing the change bitset) stays under 5 percent of the tick's own compute time at 1, 10 and 100 percent of the entities changing per tick, the serialization running on the I/O executor. Refuted by a share of 5 percent or more at any fraction.
2. **The latency of an edit.** The latency from a `set` command to its value in the live-value stream is at most one tick plus one period. Refuted by a latency above two ticks at any fraction.
3. **The size of a change set.** It grows with the fraction and not with the tick count (the mean of the second half of a run within 10 percent of the first half's), and the message per period at 100 percent stays below the full-state read's bytes.
4. **Interference.** A stepped agent session on a second world of the same process, stepping batches of ten ticks, loses under 5 percent of its throughput while the editor session runs at 100 percent beside it. Above 5 percent, the program names the shared resource: the pool when the loss falls under the threshold with one pool per world, the processor's cores otherwise.

A side question rides on the third hypothesis: whether interned names pay for an editor session. Every message is measured with names as strings and as integers.

## Method

Per worker count and per fraction: a paced run without session for 3 seconds, a paced run with the extraction alone for 3 seconds, and the session's run over the loopback socket (and in process at 4 workers), which lasts the 10 seconds of the drag plus the transaction. Every run's per-tick hashes are compared with the sequential oracle given the same input records at the same ticks; the outcomes of every command, the transaction's result and its inverse are compared with the oracle's; the client's copy of the watched component, built from the change sets alone, is compared with the host's at the end. Per tick the stepping thread records the time of each part, the pacing sleep excluded; the figures are medians over the ticks after ten settling ticks. Per delivery the I/O executor records the rows, the bytes and its own time.

Then, per worker count, three rounds of: the agent alone on its world for 2 000 ticks; the agent beside the editor session on another world, both worlds on one pool; and, at 4 workers, the same with one pool per world. The agent's throughput is the best of the three rounds. Every agent run is compared with the oracle of the same script, every editor run with the oracle of its records.

The self-checks (`cargo test -p control-surface-editor-rate`) verify on the small size that the world reproduces the sequential reference without commands and agrees with the oracle with kicks, sets and transactions at 1, 2, 3 and 8 workers in batches of 1, 7 and 40; that two worlds stepped from two threads on one pool each match the oracle; that a transaction with one stale set writes nothing and names the set, and that its inverse restores the fields; that the pool serves a job, withdraws the tickets nobody took and drops cleanly; that every message round trips with string and interned names and has the predicted size, and that an unknown name, a field that cannot be set and a truncated message are errors that say why; that both transports deliver in order; that the sampling system writes every slot once per period; and that the whole report runs with every check passing.

## What it does not measure

- A session whose period differs from the tick rate, a slow or stalled client, and several editor sessions on one world: here one delivery covers one tick, so the coalescing over several ticks is built and checked by the client's copy but never under load.
- The client's side: decoding, the editor's own data model, drawing.
- A change set computed from change ticks on the I/O executor alone. The stepping thread computes the tick's bitset here, which is the cost under test.
- A partition of the world, per-field change detection, a component whose rows have different sizes.
- A second transport channel for the data plane, shared memory, flow control, a dropped or coalesced delivery under back pressure.
- The pool of the engine. The pool here binds a helper to one world for a whole step, and the agent goes through the typed in-process path, so the interference figures bound this arrangement only. With one pool for both worlds at 4 workers the editor world's tick mostly runs on its calling thread alone, because the agent's batches hold the helpers: the editor's tick time beside the agent is reported for that reason.
- The undo stack: the inverse is computed, returned and compared with the oracle's, never applied by the session.

## Environment

Research CI, workflow `research-ci.yml`, five cells (see [`spikes/README.md`](../README.md)), run on demand with `-f spike=control-surface-editor-rate`. Rust toolchain pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), release profile, default target features of each target, standard library only. The whole run takes about three minutes, most of it the paced runs' wall time. Timings from hosted runners compare per processor only, and a hosted runner has 4 virtual CPUs (3 on macOS) for the world's team, the I/O executor, the client and, in the interference runs, a second world.

## Result

Local run of 2026-11-09 on an AMD Ryzen 9 9950X3D (16 cores, 32 threads, Windows 11, native MSVC), outside the matrix. The results of the five cells follow under "Result on the five cells". Every check passes: the 9 session runs, the 12 paced runs without session and the 24 world runs of the interference rounds match their oracles at every tick, every command's outcome and every transaction's inverse equal the oracle's, and the client's copy of the watched component equals the host's.

- **The stepping thread's share: holds.** The admission and the publication cost 4.0 to 6.5 microseconds per tick, 0.26 to 0.79 percent of the tick (worst at 4 workers and 100 percent), against a threshold of 5 percent; with the extraction charged to the session as well, 0.72 to 1.87 percent. The comparison of whole runs cannot resolve a cost this small on this machine: the median tick of two paced runs that differ by a few microseconds of sampling differs by up to 28 percent (1 183 and 1 517 microseconds without session at 1 worker, at 1 and 10 percent), so the run with the session lands between 10.9 percent below and 0.4 percent above the run with the extraction alone, and between 6.3 percent below and 22.8 percent above the run without extraction. The directly measured share is the figure; the differences between runs are reported so that nobody reads them as one. A paced tick costs more than the same tick in a batch (822 microseconds at 4 workers here, against 453 in the agent's batches), since every tick starts with cold caches and parked helpers.
- **The latency of an edit: holds.** Over 12 000 commands per run, the median is 16.6 milliseconds in every run, the 99th percentile 17.1 to 17.6 and the maximum 17.9 (4 workers, 100 percent, loopback socket), against a threshold of 33.3: one period, because the client sends at a delivery, the next tick boundary admits the command and the delivery after that tick carries it. Every command came back in the live-value message of the next tick. In process the 99th percentile is 17.1 to 17.2 milliseconds. All 12 000 `set` commands of every run applied, none was stale, and the closing transaction of 20 field sets applied with its inverse.
- **The size of a change set: holds.** The message as sent (canonical rows, string names) is 2 562, 24 162 and 240 162 bytes at 1, 10 and 100 percent (24 bytes per changed entity and a header of 162), identical at every delivery of a run, so the second half over the first is 1.000; the full-state read is 410 278 bytes. One delivery covered one tick in every run. The I/O executor spends 117 to 128, 178 to 189 and 806 to 825 microseconds per delivery over the loopback socket at the three fractions, and 12, 18 and 84 in process.
- **Interned names.** With canonical rows the names are in the header: interning saves 124 bytes of a change set whatever its size (0.05 percent at 100 percent). It pays where a name travels per value: a live-value message of 100 fields is 2 439 bytes with string names and 1 429 with integers, a `set` command 64 and 35 bytes. Were the rows name-tagged, as a control plane message is, the change set at 100 percent would be 1 320 054 bytes with strings and 320 030 with integers, both above the canonical 240 162, and the full-state read 2 460 073 and 630 032.
- **Interference: holds.** At 1 worker the agent steps 852 ticks per second alone and 834 beside the editor session, a loss of 2.2 percent. At 4 workers, 2 209 alone, 2 211 beside the editor session on one shared pool and 2 209 with one pool per world: no loss. On the shared pool the editor world pays instead: its tick takes 1 355 microseconds beside the agent against 798 alone (765 with its own pool), 8 percent of its period, because the agent's batches hold the helpers. This machine has four times the cores the two worlds, the I/O executor and the client need; a hosted runner does not, and the cells' figures will say what the cores cost.

The raw measurements of the local run are not published; the cells' are the artifacts of the research CI run named below. The result holds for the reference workload version 1 at this toolchain, on this machine, for the arrangement described above.

## Result on the five cells

Research CI [run of 2026-11-09](https://github.com/ludenea/ludenea/actions/runs/42694659908). Every world matches its oracle and every delivery check passes on every cell.

- **The stepping thread's time on behalf of the session: holds on every cell.** 4 to 27 microseconds per tick, 0.2 to 2.7 percent of the tick's compute time, the highest at a fraction of 100 percent; the extraction adds 12 to 49 microseconds.
- **A set command to its live value: holds on four cells, fails on `macos-arm64`.** One tick on the Linux and Windows cells (16.6 to 16.7 milliseconds at the median, 17.3 at the 99th percentile, 22.1 at most). On the macOS runner 42 to 53 milliseconds at the median and up to 156, at 1 worker as at 4: the host keeps 60 ticks per second there, but the thread standing for the I/O executor delivers 215 to 246 times in ten seconds instead of 600, its period timer overshooting, each delivery coalescing up to 10 ticks.
- **The change set's size: holds on every cell.** 2 562, 24 162 and 240 162 bytes per period at 1, 10 and 100 percent, constant over the run, against 410 278 for the full-state read.
- **The agent's loss beside the editor session: holds on the two Windows cells, fails on the two Linux cells and the macOS runner.** 1.4 and 4.4 percent on `windows-arm64` and `windows-x86_64` at 4 workers; 8.2 and 6.1 percent on `linux-arm64` and `linux-x86_64` at 4 workers (under 1 percent at 1 worker); 8.3 percent on `macos-arm64` at 1 worker. With one pool per world the loss stays (0.9 to 6.8 percent): the shared resource is the processor's cores.
