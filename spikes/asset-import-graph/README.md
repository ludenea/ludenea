# Import graph

Throwaway spike of the assets research. It generates a synthetic content root (tables with a sidecar file, sheets that hold several sub-assets, scenes that carry their identifier in the file), imports it with a pipeline built as a build system is built (one canonical action per asset, one presentation action per asset and variant, each keyed by what it reads, on a pool with one central ready set), and measures, instead of assuming: whether the domain content set is one whatever the worker count, the target and the cell; whether a graph built in two passes, where an import that asks for an artifact not built yet ends with a request and is run again, gives the manifest of a graph declared in advance, and what the ready set costs on many small actions; whether a cascade stops where bytes stop changing; whether the action key is complete; what a pass that finds nothing to do costs with a change journal; whether a revision is atomic when the importing process is ended from outside; whether a package is a function of its inputs and what a mount order does; and what the import of a scene-sized text source costs per prototype.

The [parallel import spike](../asset-import-parallel/README.md) measured the import of one kind of asset with no identity, no manifest and no target; this spike measures what a pipeline is built of around it. Nothing here is the engine's importer, pool, cache or package format.

## Layout

- `src/content.rs`: the content root, every file a function of the size and of a seed. Tables (`key;value;name` records, a comment line allowed) with a sidecar that holds their identifier: half of them are the palettes of the sheets, half are used by the scenes. Sheets (a header of text lines, then raw pixels) with a sidecar, each with eight sprites and two clips; a clip names sprites of its own sheet by their key. Scenes (text, their identifier in their first line, no sidecar): one entity prototype per line, naming a component type of the schema, some using a table, a clip or, in every second scene, the scene before it; and one scene of 10 000 prototypes. One sprite in six and one scene in four name a dependency as late: the describe function does not report it and the import discovers it. The file also holds the edits the scenarios make (a comment added, values changed, a rewrite in place with the modification time set back, a sheet copied under a new identifier or with its identity, content added).
- `src/formats.rs`: the importers as two functions in plain data. The describe function gives the assets a source holds (each with its key and its type) and the dependencies known without doing the work. The import function gives the canonical part of one asset; what it needs beyond its source it asks of its context (the canonical part of another asset by identifier, an entry of the schema by name), which records each read with the hash read; where the part asked for is not built yet, the import ends with a request. The context of a canonical import holds no target. An identifier is 128 bits: drawn for a source, derived from the source's identifier and the sub-asset's key for a sub-asset. A clip's part references its siblings by key and the pipeline resolves them to identifiers before the part is hashed. Every part an importer returns is validated before it is stored. The presentation encoder mixes the index of the worker that runs it into its payload: it is deliberately not reproducible.
- `src/pool.rs`: dependency counting with one central ready set under one lock, any free worker claiming the next ready action. An action that ends with a request waits behind the action it asked for and is run again from its start; no action adds an action from inside a worker. A cycle of requests fails the actions on it, naming the cycle; an action that asks twice for the same output fails; where nothing runs and nothing is ready, what is left fails. The pool measures the share of their time the workers spend outside an action.
- `src/pipeline.rs`: the cache (a content map from a hash to bytes; an action map from an action key to a trace: the output hashes and the reads with the hash each read), in memory and optionally mirrored on disk, every file written under another name then renamed. A lookup is in two steps: the key matches, then every recorded read still has its hash. The key of a canonical action is the digest of the source bytes, the importer's name and version, the settings of the sidecar, the source's identifier and the sub-asset's key, the schema entry of the asset type and the version of the canonical form; the key of a presentation action adds the hash of the canonical part, the variant key and the platform. A pass runs the describe actions (per source: its size and modification time and its sidecar's, its digest and identity from the change journal where those facts are unchanged and the journal is trusted, its description from the cache), then the import actions on the dependencies the descriptions and the traces give, then writes the domain manifest, one presentation manifest per target profile and the root document that names their hashes, put in place by one rename. A pass with a failed action puts no revision in place.
- `src/package.rs`: a package (the artifacts of the entries in the order of the asset identifiers, then one index block, no timestamp and no name), the closure of roots through the domain manifest, the entries of a later package computed from two manifests, and the mount of packages in an order with or without leave to override.
- `src/main.rs`: the scenarios, the report, and the importing process the atomicity scenario starts and ends.

Hashes are FNV-1a 64 as in the spikes before this one: a stand-in, not a choice of content hash.

## Hypotheses

Stated before the run. The set: 128 tables of 12 000 records, 64 sheets of eight sprites of 256 by 256 pixels and two clips, 32 scenes of 400 prototypes and one of 10 000: 225 sources, 801 assets, 163 MB. Two target profiles of two variants each. One pinned Rust toolchain, default target features, worker counts 1, 4 and 8.

1. One domain set. The domain manifest's hash is the same on the five cells, at 1, 4 and 8 workers, for the two target profiles and with the presentation actions off; the presentation manifests differ between profiles and may differ between runs. Any difference in a domain manifest refutes it.
2. The two-pass graph on the ready set. With the describe actions first and imports that end with a request for a part not built yet and are run again (about a tenth of the imports name a dependency the describe function does not report), the manifest equals the one obtained with every dependency declared in advance; the work run twice is recorded for both placements of the request, before the computation and after it (no threshold: the figure is the synthetic importer's own). On a graph of 100 000 independent actions of under 50 microseconds each, the workers spend under 10 percent of their time outside an action at 8 workers on the founder's machine. A planted cycle of two requests fails both actions, naming the cycle. A differing manifest, a share above 10 percent, or a pass that does not end refutes it.
3. The cascade stops where bytes stop changing. A change of a source that leaves its canonical part unchanged runs its own actions and none downstream; a change of a shared dependency runs exactly its dependents. One action more or less than the expected count refutes it.
4. The key is complete. A schema entry an importer reads is changed with no source changed: the assets whose import read it are imported again, and no other. A source that holds several sub-assets is copied and the copy given a new identifier: the copy's parts name the copy's siblings. A part served from the cache that should have been rebuilt, or a copy that names the original's siblings, refutes it.
5. The change journal. A pass that finds nothing to do costs under 5 percent of a full import with the journal, against the 14 to 22 percent the parallel import spike measured without one; a source rewritten in place with the same size and its modification time set back is the case the journal misses, and the hermetic mode that ignores the journal finds it. A cost above 5 percent, or a hermetic pass that misses the change, refutes it.
6. A revision is atomic. The importing process is ended from outside at 50 random moments; after each, a reader obtains the former revision or the new one, verified by its hash, and every cache entry present is valid under its key. One unreadable or mixed revision refutes it.
7. A package is a function of its inputs. Two builds give byte-identical package files for the domain slice always, across cells included, and for the presentation slice where both take their payloads from one cache; a second package mounted after the first with leave to override does so for the entries it names and no other, and without that leave is refused for each entry already mounted. One differing byte refutes it.
8. A scene-sized text source. The import of a text source of 10 000 entity prototypes into canonical bytes, with its validation, is timed per prototype (recorded, no threshold).

## Method

- One domain set: a full import from an empty cache at each worker count for each of the two profiles and with no profile, a second import of the first profile at 8 workers, and one import for the two profiles together (each canonical action must run once). The summary counts the distinct domain manifest hashes across the cells.
- The two-pass graph: three full imports at 8 workers with no profile (requests placed before the computation, as the interface asks; requests placed after it; every dependency declared by the describe functions), each reporting the imports that ended with a request, the time those runs had spent, and its manifest. Then 100 000 actions with no dependency, each digesting 16 KB, on the pool alone at 1, 4 and 8 workers. Then a content root of two scenes that each use the other as late.
- The cascade and the key: one cache, the first profile, 8 workers, every pass hermetic. After the full import: a comment added to the first palette table; its values changed; the values of a table the scenes use changed (the scenes embed its record count, which does not change); a field added to the schema entry of the velocity component; the first sheet copied under a new identifier; the second sheet copied with its identity. The expected actions of each re-import are computed from the generator's rules and compared, as sets of assets for the canonical actions and as counts for the others.
- The change journal: three full imports at 8 workers from empty caches with the journal on, the best taken; then five passes with nothing to do with the journal and five without (hermetic: every source read and digested), the best of each against the best full import. A table is then rewritten in place with one digit changed, at the same size, and its modification time set back: one pass with the journal, one without. Added after the first local measurement, which found the journal's pass above the threshold with most of its time in the scan: the same five passes with the files' sizes and modification times taken from the directory listing instead of asked file by file. Every pass reports the time of its scan, its graph, its import actions and its revision.
- A revision is atomic: a small content root (56 assets) and a cache on disk. The spike starts its own binary as the importing process; three uninterrupted passes, each after a change, give the usual duration; then 50 times: three tables are changed, the process is started and ended after a delay drawn between zero and 1.2 times that duration, a reader in the parent opens the cache from disk (every object read is verified against the hash that names it) and reads the root, the manifests and every artifact they name, and the cache directory is walked (every object must hash to its name, every action entry must decode and name outputs that are present; a file that was never renamed is no entry). The new revision's domain manifest is known from a pass the parent runs in memory.
- Packages: from the revision of the journal scenario's cache, a package of the scenes and their closure, the domain slice alone and with the first profile's payloads, each built twice; the same from a second cache imported from nothing. Then two tables are changed and a table and a scene are added, and the later package holds what the two manifests say is new; it is mounted on the first with and without leave to override, on two instances.
- The scene-sized source: the import function on the scene of 10 000 prototypes, with its validation, five times, against the parts of the last revision.

The self-checks (`cargo test -p asset-import-graph`) verify the formats and the importers one by one (a table is sorted and a comment changes nothing; a sheet describes its assets and a late palette is a request under both placements; a clip names the siblings of its own source; a scene reads the schema and the assets it uses, and another schema entry changes its part; an identity is read beside a foreign source; the encoder is not reproducible), the pool (a dependent never runs before its dependency at 1, 3 and 8 workers; a request runs the action again; a cycle of requests fails the actions on it and its dependent, and the run ends; a repeated request, a declared cycle and a failed dependency fail), a cut package, a corrupt package and a cut trace, and every scenario on a small set, the importing process run inside the test process and ended by nothing.

## Environment

Research CI, workflow `research-ci.yml`, five cells (see [`spikes/README.md`](../README.md)), run on demand with `-f spike=asset-import-graph`, in the release profile and, for the identities and the counts, in the unoptimized profile (`-f profile=dev`), which measures a smaller set (65 sources, 209 assets) and says so in its report. Rust toolchain pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), default target features of each target. Standard library only, plus the reference workload crate for its JSON writer, its FNV-1a hash and its random stream. The two magnitudes with a threshold (the ready set's share and the journal's pass) are judged on one quiet machine outside the matrix (an AMD Ryzen 9 9950X3D, 16 cores and 32 threads, Windows 11); the hosted runners give the ordinal reading. The content root, the caches and the scratch files live under the system's temporary directory and are removed at the end.
