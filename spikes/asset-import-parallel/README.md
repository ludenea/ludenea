# Parallel asset import

Throwaway spike of the assets research and of the background pool of the multithreading research (throughput-bound work outside the frame, the second half of the engine's concurrency model). It generates a few hundred synthetic source assets of a plain kind (record tables imported by integer arithmetic), a geometric kind (meshes imported by the IEEE-exact floating-point operations only) and a control kind (the same meshes normalized with the platform math library), imports them in parallel on a background pool with dynamic claiming into canonical content-hashed bytes, and measures, instead of assuming: whether the outputs are byte-identical across runs, worker counts and the five cells of the research CI; whether a re-import after one source changes imports that asset and its dependents only, by the action keys and the cache; how the import's throughput scales with the workers and what the dependency structure costs the pool; and whether the order in which the pool completes the actions differs between runs while the outputs do not. Throwaway, never product code: nothing here is the engine's importer, pool or asset format.

## Layout

- `src/sources.rs`: the synthetic source assets, generated deterministically from a seed into a temporary directory (`std::env::temp_dir()` under a directory named after the spike and the process identifier, removed at the end). Plain kind, 200 files: a record table as text, one record per line (`key;a;b;c;d;name`: a `u32` key, integers of 8, 16, 32 and 64 bits, a name of 1 to 16 lowercase letters), 400 records with a few repeated keys. Geometric kind, 200 files: a binary mesh of 24 000 vertices (`f32` positions, 24-bit integers scaled into a cube by exact operations) and 48 000 triangles (`u32` indices). Control kind, 50 files: the same mesh format. Every mesh depends on one plain asset, its transform table, whose first record gives the mesh's scale and offset; a transform table is shared by 8 meshes (25 tables for the geometric meshes, 7 for the control meshes), the other 168 plain tables have no dependent. Every source is a function of the seed and nothing else, so the same files exist on every cell. The set is 220 MB of sources and 255 MB of outputs; it is sized so that one full import at 1 worker takes about half a second on the founder's machine, which is 1 to 1.5 seconds on a hosted runner.
- `src/import.rs`: the importer as a hermetic action. Its key is the FNV-1a 64 digest of the source bytes' digest, the importer's name and version, the import settings (the quantization bits), the target platform name (a constant, since the output must not depend on the platform) and the content hashes of the outputs of the actions it depends on, every variable-length part prefixed by its length. Its output is canonical bytes: a 12-byte header (magic `LDNA`, format version, kind tag, a reserved byte, importer version), little-endian fields in a fixed order, then the body; its content hash is the FNV-1a 64 digest of those bytes. The plain importer parses and validates the records, sorts them by key (stable, so the file order decides among equal keys), deduplicates by key, computes the prefix sums of one field and the checksum of the record bytes, and emits the record count, the records, the prefix sums and the checksum. The geometric importer applies the transform (a multiplication then an addition, never contracted), recomputes the vertex normals from the faces (the sum of the face normals in triangle order, normalized with `f32::sqrt`), the bounding box and sphere, quantizes the positions to 16-bit integers inside the bounding box, reindexes the vertices in a canonical order (by quantized position, then by original index) and emits the counts, the bounds, the sphere, the vertices (quantized position and normal) and the triangles. Only addition, subtraction, multiplication, division, `sqrt`, comparisons and conversions appear in it: no platform math library function, no `mul_add`. The control importer is the geometric one with the normalization computed as `n * exp(-0.5 * ln(n . n))` through the platform library's `ln` and `exp`. The decoders of both kinds refuse truncated, trailing, corrupt or mislabeled bytes with a reason. The cache maps action keys to outputs, in memory and mirrored on disk in the temporary directory, one file per key, so that a second process could hit it.
- `src/pool.rs`: the background pool. `workers` threads that live until the pool is dropped; a set of actions is submitted as a batch; an action becomes ready when every action it depends on has completed (dependency counting); any free worker claims the next ready action; a worker with nothing ready parks on the batch's condition variable; the submitting thread returns when the whole set has completed; the workers park until the next batch or the pool's drop, which joins them. The pool asserts that a claimed action's dependencies have completed, records the sequence in which actions completed and the time every worker spent waiting for a ready action. A failed action fails its dependents with the reason and nothing else. No priority and no core budget in this spike: it measures the claiming and the dependency counting alone.
- `src/main.rs`: the scenarios and the report, one JSON document on standard output.

## Hypotheses

Compiled by the pinned Rust toolchain at default target features, worker counts 1, 2, 4 and 8, plus 16 when the machine has at least sixteen hardware threads, plus the machine's available parallelism when it is not among them:

1. Byte-identical across runs and worker counts. The manifest of a kind (the sorted list of asset identifier and content hash, hashed as a whole) is identical across three runs at each worker count and across all worker counts, on each cell, for the plain kind, the geometric kind and the control kind alike: the order in which the pool imports never changes an output. The report gives the manifest hash per kind, per run and per worker count, and the count of distinct values per kind; any count above 1 refutes the hypothesis.
2. Byte-identical across cells for the plain and geometric kinds. The manifest hashes of the plain and geometric kinds are the same on every cell: the plain importer is integer arithmetic, and the geometric importer obeys the permitted floating-point configuration (exact operations, no contraction, no platform library) with engine-owned math. The control kind is expected to split the cells, as the reference workload's wander system did when it used the platform library, though the platform facts spike found the `f32` probes of the library identical across the cells, so the split is a question and not a prediction. The spike cannot see other cells: it reports its per-kind manifest hashes at the top level of its report, and the summary counts the distinct values across the cells. More than one value for the plain or the geometric kind refutes the hypothesis.
3. Incremental re-import. After one plain source that 8 geometric assets depend on changes by one byte, a re-import imports exactly that asset and its 8 dependents (9 actions) and nothing else; after one geometric source changes, exactly 1; after no change, 0, also with a fresh cache that only has the disk mirror; after the importer's version changes, every asset (450). The content hashes of the untouched assets are unchanged. The report gives the action counts, the cache hits and the elapsed time of each re-import against the full import.
4. Throughput scales with the workers. The full import's wall time at each worker count, best of three alternating rounds after a warm-up import, each round from an empty cache, gives a speedup over 1 worker. Refuting thresholds, stated for the environment: below 1.6 at 4 workers on the x86_64 runner cells (two cores with hyperthreads), below 3.0 at 4 workers on the ARM64 runner cells (four cores), below 10 at 16 workers on the founder's machine (16 cores). The report also gives the pool's idle share (the sum over workers of the time spent waiting for a ready action, over the workers' wall time), which measures what the dependency structure costs the pool: the meshes wait for their transform tables.
5. The claiming order is not the output order. In two runs at 8 workers, the sequence in which the actions completed differs (the sequence's hash differs) while the manifest hash is the same; if two runs happened to complete in the same order, the report says so and a third run is taken (up to five). This makes the first hypothesis a measurement and not a tautology.

## Method

The host generates the set once from a fixed seed, then runs the scenarios in this order, the timed one last. Identity: for every worker count, one pool and three runs, each from an empty in-memory cache, so that every action imports; the manifests of every run are compared and the first run's manifests are written at the top level of the report. Incremental: one pool of 8 workers and a cache mirrored on disk; a full import, then the re-imports (no change; no change with a fresh cache that reads the mirror; one geometric source altered by one low mantissa bit of its first coordinate, then restored; the first transform table altered by one letter of a name, then restored; the importer version raised by one), each compared with the full import for the exact set of actions imported and for the content hashes of the untouched assets. Claiming order: up to five imports at 8 workers from empty caches, stopped at the first pair of runs whose completion sequences differ. Throughput: one pool per worker count created before the timing, a warm-up import, then three alternating rounds (every worker count once per round), each import from an empty in-memory cache, timed from the submission to the last completion; the best round of each count is the figure and the speedup is the 1-worker figure over it. Every scenario checks that no action failed.

The self-checks (`cargo test -p asset-import-parallel`) run on a small set (20 plain, 20 geometric and 5 control assets, 40 records per table, 300 vertices and 600 triangles per mesh) and verify that the canonical bytes of each kind round trip (header, fields, body) and are refused with a reason when truncated, trailing, corrupt or mislabeled; that the importers refuse bad sources and bad dependencies with a reason; that the plain and the geometric importers are pure functions of their inputs and that the dependency's output is one of them; that the action key changes when any of its inputs changes and only then; that the cache serves memory then the disk mirror; that the generated set has the announced counts and dependencies, the same bytes for the same seed, and is removed when dropped; that the pool never completes a dependent before its dependency at 1, 3 and 8 workers, passes the right dependency outputs, lets any free worker claim the next ready action, fails a dependent of a failed action and nothing else, parks when the set is imported and exits when dropped; that the manifest hash is the same at 1, 2, 3 and 8 workers and equal to a sequential import's; that the incremental counts (0, 0 from the disk mirror, 1, 9, all) hold with the untouched hashes unchanged; and that the whole report runs on the small set with every check passing.

## Environment

Research CI, workflow `research-ci.yml`, five cells (see [`spikes/README.md`](../README.md)), run on demand with `-f spike=asset-import-parallel`. Rust toolchain pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), release profile, default target features of each target, standard library only, the reference workload crate for its JSON writer and its FNV-1a hash. Plus a local run on the founder's machine outside the matrix: an AMD Ryzen 9 9950X3D (16 cores, 32 threads), Windows 11 Professional build 26200, the native MSVC toolchain, worker counts 1, 2, 4, 8, 16 and 32, taken while another spike was built and run on the same machine. Timings from hosted runners compare per processor only; the x86_64 runners have two cores with hyperthreads, the ARM64 runners four cores, so their speedups are bounded by those counts.

## Result

Local run on 2026-11-09 on the founder's machine (AMD Ryzen 9 9950X3D, 16 cores and 32 threads, Windows 11 Professional build 26200, native MSVC toolchain, rustc 1.99.1, worker counts 1, 2, 4, 8, 16 and 32), taken while another spike was built and run on the same machine; its three rounds per worker count agree within 4 percent, so it is the run kept; the five cells follow in the next subsection. The set is 450 assets, 220 368 282 source bytes and 254 599 041 output bytes.

- Hypothesis 1 holds locally: the 18 imports of the identity scenario (three runs at each of six worker counts) give one manifest hash per kind (plain `0xecef84dcdc11edbd`, geometric `0x898b94f0b7c6a6d9`, control `0xff7d54fc1e05a1b7`, all `0xd99b711b07eeba6f`), one distinct value per kind, no failed action; the warm-up and the eighteen timed imports of the throughput scenario and the imports of the other scenarios give the same manifests.
- Hypothesis 2 cannot be measured on one machine: the plain and geometric manifest hashes above are the values the cells must give; the control's value is reported for the comparison, with the question of whether the `f32` `ln` and `exp` of the platform libraries split the cells left to the run.
- Hypothesis 3 holds locally: the full import at 8 workers imports 450 actions in 142 ms and mirrors 450 files (254 599 041 bytes) on disk; the re-import with no change imports 0 actions (450 memory hits) in 26 ms; a fresh cache on the disk mirror imports 0 (450 disk hits) in 40 ms; one geometric source altered by one byte imports exactly 1 (449 memory hits) in 26 ms; the transform table shared by 8 meshes altered by one byte imports exactly 9, the table and its 8 dependents (441 memory hits), in 29 ms; the importer version raised imports all 450 in 161 ms. The untouched assets keep their content hashes in every case. A re-import that imports nothing still costs 18 percent of the full import: it reads and digests every source (220 MB) to compute the keys, which is what a content-addressed key costs without a change journal.
- Hypothesis 4 holds locally: the full import's best wall times are 507 ms at 1 worker, 255 at 2, 131 at 4, 70 at 8, 44 at 16 and 39 at 32, speedups of 1.99, 3.87, 7.28, 11.55 and 13.07, above the refuting threshold of 10 at 16 workers; the idle share of the pool is 0.3 percent at 2 workers, 0.6 at 4, 1.1 at 8, 2.3 at 16 and 3.7 at 32, so the dependency structure costs the pool almost nothing (the 200 plain tables are ready at once and the meshes become ready as the tables complete). What caps the speedup at 16 and 32 workers is not the pool: the 450 actions read 220 MB of sources and write 255 MB of outputs through the memory system, and the second hardware thread of a core adds 13 percent over the first.
- Hypothesis 5 holds locally: the two runs at 8 workers completed in different sequences (hashes `0xf14d9233ff702624` and `0xe6dcfd4a6ac416e4`, the first six completions `plain-000, plain-001, plain-002, plain-003, plain-005, plain-008` against `plain-001, plain-003, plain-002, plain-000, plain-004, plain-006`) with the same manifest, at the first attempt.

The local result holds for this set, this toolchain and the founder's machine.

- Hypothesis 1 holds on every cell: one manifest per kind across the three runs at every worker count and across the worker counts, for the plain, geometric and control kinds alike, with no failed action.
- Hypothesis 2 holds: the plain manifest and the geometric manifest are the same on the five cells and on the founder's machine, so the engine-owned geometric importer under the permitted configuration (exact operations, no contraction, `sqrt` only) gives byte-identical outputs across the boundary on 200 meshes of 24 000 vertices. The control kind splits the cells three ways, into the same three classes as the reference workload's wander system did with the platform library's `f32` cosine and sine: Linux x86_64, Linux ARM64 and Windows ARM64 agree, macOS differs, and Windows x86_64 differs again (its value is the founder's Windows x86_64 machine's too). The eight `f32` probes of the platform facts spike, which agree on the five cells, did not predict the split; the 50 control meshes feed the library's `f32` `ln` and `exp` a vertex-sized sample of arguments, and that is enough.
- Hypothesis 3 holds on every cell: exactly 0, 0, 1, 9 and 450 actions re-imported, the untouched assets' content hashes unchanged, 450 memory hits then 450 disk hits for the no-change passes. The no-change re-import costs 14 to 22 percent of the full import on four cells (56 to 122 milliseconds), the fresh cache fed from the disk mirror 21 to 45 percent (97 to 243 milliseconds), the importer version change 98 to 120 percent. On Windows x86_64 the full import of this scenario, the first to write the 255 MB mirror on that runner's disk, took 1 499 milliseconds against 298 in the throughput scenario, so its ratios (5 to 28 percent) measure that slow first write and not a faster re-import (74 milliseconds, in line with the other cells).
- Hypothesis 4 holds on every cell: speedups of 3.22 and 3.14 at 4 workers on the x86_64 cells (threshold 1.6; two cores with hyperthreads, whose second thread carries almost a core's worth here because the import is memory and I/O work that leaves the execution units idle), 3.93 and 3.69 on the ARM64 cells (threshold 3.0; four cores), 2.63 at 3 workers and 2.64 at 4 on the 3-CPU macOS cell. Two workers are linear (1.84 to 2.00). Eight workers on four CPUs neither gain nor lose (minus 6 to plus 1 percent against 4 workers), the idle share 1.1 to 4.3 percent. The macOS cell's rounds vary by up to 74 percent (596 against 343 milliseconds), as in the earlier spikes; the best round is kept.
- Hypothesis 5 holds on every cell at the first attempt: the two runs at 8 workers completed in different sequences with the same manifest.

The result holds for this set, this toolchain, these runner images and the founder's machine.
