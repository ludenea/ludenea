# Plugin tiers

Throwaway spike of the plugin architecture research. It takes one system of the [reference workload](../reference-workload/README.md), the motion pass (positions integrated from velocities, bounced on the walls, the chunk's kinetic energy summed in slot order), implements it once as a plugin and reaches it through each candidate plugin tier from inside the [runtime skeleton](../runtime-skeleton/README.md) spike's world: a crate linked at compile time, a WebAssembly module run by an embedded runtime, a dynamic library with a C ABI built in Rust by the engine's toolchain and in C by the platform's compiler, and, for the extension that fits it, an out-of-process importer. It measures, instead of assuming, whether every tier gives the reference hashes at every worker count on every cell of the boundary, what each tier costs per chunk against the kernel inlined in the world, whether a reload of the module or of a library between two ticks changes a hash, what a C compiler's default floating-point flags do to a pass the tier cannot inspect, and what an importer's round trip costs.

## Layout

- `src/world.rs`: a trimmed copy of the runtime skeleton spike's core (no snapshot, no injection, no extraction): the reference workload stepped on the dependency-counting tick graph, stepped by whole ticks, a panic in a task caught at the task boundary and failing the world. The one change: the motion node dispatches to a motion pass chosen at creation, the kernel inlined as the skeleton has it (the built-in pass, the baseline) or an implementation of the `MotionPass` extension point, and charges the processor time of every motion chunk to the node.
- `motion-crate/`: the plugin, one Rust implementation of the pass over one chunk's columns with the reference workload's own kernels, in two forms: safe slices, and raw pointers with the plain-data signature every boundary carries (`motion(x, y, mass, alive, next_x, next_y, next_vx, next_vy, count, tick) -> energy`).
- `src/tiers.rs`: the adapters behind the extension point: the compile-time tier (the crate linked statically, one trait object call per chunk) and the dynamic native tier (a library loaded at run time whose `motion` symbol the chunks call through a function pointer, reloadable between two steps). `src/dynamic.rs` reaches the platform's loader directly (`dlopen`, `dlsym`, `dlclose`; `LoadLibraryW`, `GetProcAddress`, `FreeLibrary`).
- `motion-module/`: the plugin exported as a WebAssembly module (a `cdylib` built for `wasm32-unknown-unknown`). `src/module.rs`: the sandboxed tier, the module compiled and run by Wasmtime, one instance per worker thread (held in a thread-local slot, so that a chunk reuses the instance its thread used last and no lock sits on the hot path; a first version pooled the instances behind a lock, and at 8 and 10 workers the lock's parking and the instances migrating between cores cost ten times the pass), the chunk's columns copied into a page of the module's memory before the call and the four written columns copied back after it, the copy and the call timed separately; a reload compiles the module again from its file and retires every instance, each worker instantiating the new module on its next chunk.
- `motion-native/`: the plugin exported through a C ABI from a Rust dynamic library (a `cdylib` built by the pinned toolchain, release profile). `motion-c/`: the same pass in C with its `CMakeLists.txt`; the option `MOTION_PERMITTED` adds the permitted floating-point configuration (`-ffp-contract=off` for GCC and Clang, `/fp:strict` for MSVC), off it leaves the compiler's defaults. The energy's `(vx * vx) + (vy * vy)` is the contraction candidate.
- `src/builds.rs`: the run-time builds the spike performs in temporary directories: `rustup target add wasm32-unknown-unknown` then `cargo build --release --locked --target wasm32-unknown-unknown -p motion-module`; `cargo build --release --locked -p motion-native`; the C library twice with CMake in release mode (configure, build, install), the compiler and flags CMake used recorded by the CMake file.
- `src/importer.rs`: the out-of-process tier measured on what fits it: the spike binary started with `--importer` reads one line naming a source file on its standard input (two fields, the specification's repulsion constants) and answers on its standard output with the canonical bytes it produced (two little-endian `f32` fields and their FNV-1a 64 content hash); the host spawns it, measures the spawn plus round trip, checks the bytes and records the content hash as an input before the first tick. A system runs inside the tick, so the pass itself cannot be a process; this tier is measured on the importer only.
- `src/main.rs`: the scenarios and the report. `tests/tiers.rs`: the self-checks.

Third-party components: Wasmtime 50.0.1 (crate `wasmtime`, Apache 2.0 with the LLVM exception, features `runtime`, `cranelift` and `std` only), the subject of the sandboxed tier's measurement and nothing else. CMake and the C compilers are the platform's.

## Hypotheses

With the reference workload, version 1, default size (10 000 entities, 1 000 ticks), wander system off (no transcendental function enters any tier), compiled by one pinned Rust toolchain at default target features, at 1, 2, 4 and 8 workers and the machine's CPU count when different:

1. The compile-time tier gives the reference hashes at every worker count on every cell, and its cost per chunk equals the built-in pass's within noise: a trait object call per chunk of 256 slots.
2. The sandboxed tier gives the reference hashes at every worker count on every cell: the module's `f32` arithmetic is IEEE 754 with no contraction, like the host's. Its cost per chunk is a few times the built-in pass's for a pass this small, the copy of the columns in and out counted apart from the call; compiling the module again and instantiating it again between two steps changes no hash.
3. The dynamic native tier in Rust (the library built by the engine's toolchain, release profile) gives the reference hashes at every worker count on every cell, its cost per chunk against the built-in pass is the lost inlining and the function pointer call, and unloading and loading the library again between two steps changes no hash.
4. The same pass in C built by the cell's default compiler with the permitted configuration gives the reference hashes on every cell; built with the compiler's default flags it gives the reference hashes where the defaults do not contract (the x86_64 cells, whose baseline has no fused multiply-add instruction; MSVC, which does not contract under its default) and different hashes from tick 1 where they do (GCC on Linux ARM64, Apple Clang on macOS, both of which fuse `(vx * vx) + (vy * vy)` into a multiply-add by default): the measured form of "the tier cannot enforce the contract". The default build's hashes are nonetheless identical across worker counts: a contraction is deterministic, only different.
5. The importer round trip (spawn the process, send the request, read 16 bytes, wait) costs milliseconds, the bytes equal the host's own import, and the content hash is what the host records as an input: the out-of-process tier's cost is a process and a transport, not a boundary call per chunk.

## Method

The binary runs the sequential reference once; builds the module, the Rust library and the two C libraries in temporary directories (every build's duration, success and, for C, compiler and flags are in the report; a build or a load that fails leaves its tier reported as unavailable with the reason, and the other tiers run); loads the module once (each worker thread instantiates it on its first chunk) and each library once; then, for every worker count, steps a fresh world of each tier through the 1 000 ticks in one call and records the run hash, the first divergent tick against the reference, the ticks per second, the motion node's processor time per tick and per chunk and its ratio to the built-in pass at the same worker count (the module adds its copy and call times per tick). For the module and the three libraries it then steps a world to tick 500 at 4 workers, reloads the code (the module compiled again from its file, a library unloaded and loaded again), steps to tick 1 000 and compares with the reference. The module's copy and call times are reported per run as the difference of its counters. Finally it spawns itself as the importer five times and records each round trip. The temporary directories are removed at the end.

The self-checks (`cargo test -p plugin-tiers`) verify on the small size over 40 ticks that the built-in pass and the compile-time crate reproduce the reference at 1, 2 and 3 workers and by batches, that a pass that panics fails its world at the motion node with the tick named, that the module and the Rust and C libraries build here, reproduce the reference where their flags permit and survive a reload at tick 17 (the default C build is checked for agreement across worker counts, since whether it contracts depends on the machine; a machine without the WebAssembly target or without CMake skips those checks with a printed reason), that the import is canonical and its errors named, and that the importer process answers the expected bytes and names a missing source.

## Environment

Research CI, workflow `research-ci.yml`, five cells (see [`spikes/README.md`](../README.md)), run on demand with `-f spike=plugin-tiers`. Rust toolchain pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), release profile, default target features of each target; the C compiler of each cell is the one CMake finds (GCC on Linux, MSVC on Windows, Apple Clang on macOS); plus a local run on an Apple M5 (10 cores, macOS 26, Apple Clang 21) outside the matrix. The x86_64 runners' 4 virtual CPUs are two cores with hyperthreads and the macOS runner has 3; 8 workers oversubscribe every cell, which the ratios must be read against. Timings from hosted runners compare per processor only.

## Result

Local validation run of 2026-11-03 on the founder's Apple M5 (10 cores: four performance and six efficiency cores, macOS 26, Apple Clang 21, CMake 4.2), outside the matrix, with the timings taken while other builds ran on the machine; the research CI run on the five cells follows. The four run-time builds succeeded (the module and the Rust library in 0.3 s each, the C library in 0.3 s per configuration, Apple Clang with `-O3 -DNDEBUG` and, for the permitted build, `-ffp-contract=off`), every tier loaded, and the sequential reference's run hash is the one of `reference-hashes.md`.

| Tier, form | Matches the reference at 1, 2, 4, 8, 10 workers | Motion node, us per chunk at 1 and 4 workers | Ratio to the built-in pass at 1, 2, 4, 8, 10 workers |
| --- | --- | --- | --- |
| built-in, inlined kernel | yes | 0.58, 0.63 | 1 |
| compile-time crate, static crate | yes | 0.57, 0.61 | 0.99, 1.07, 0.98, 0.94, 0.98 |
| sandboxed module, Wasmtime | yes | 0.93, 1.13 | 1.61, 1.52, 1.80, 1.66, 1.78 |
| dynamic native library, Rust cdylib | yes | 0.55, 0.73 | 0.95, 0.98, 1.15, 0.99, 0.98 |
| dynamic native library, C with the permitted flags | yes | 0.54, 0.60 | 0.94, 1.02, 0.96, 0.92, 0.95 |
| dynamic native library, C with the default flags | no: first divergent tick 3 at every worker count, one run hash across worker counts | 0.50, 0.55 | 0.87, 0.91, 0.88, 0.83, 0.84 |

- Hypothesis 1 holds: the compile-time crate reproduces the reference at every worker count, and its cost per chunk is the built-in pass's within noise (ratios 0.94 to 1.07 for chunks of 0.6 to 1.1 microseconds).
- Hypothesis 2 holds: the module reproduces the reference at every worker count and survives a reload at tick 500 (the module compiled again in 9.8 ms, every worker instantiating it on its next chunk, the hashes to tick 1 000 equal to the reference). Its cost is 1.5 to 1.8 times the built-in pass per chunk at every worker count: per tick at 1 worker, 5.4 microseconds of copies (6 KB in, 4 KB out, for 40 chunks) and 28.5 of calls (0.7 microseconds per call of a pass that runs 0.58 natively) against 22 for the built-in pass. The instance per worker thread is what keeps the ratio flat: pooled behind a lock, the same module cost 4.6 times the pass at 4 workers and 10 to 12 times at 8 and 10.
- Hypothesis 3 holds: the Rust library reproduces the reference at every worker count at the built-in pass's cost within noise (0.95 to 1.15), and unloading and loading it again at tick 500 (0.1 ms) changes no hash.
- Hypothesis 4 holds in both directions on this machine: the C build with `-ffp-contract=off` reproduces the reference at every worker count (and survives a reload in 0.3 ms); the C build with Apple Clang's defaults diverges from the reference at tick 3 at every worker count, with one and the same run hash across worker counts (a contraction is deterministic, only different): the compiler fused `(vx * vx) + (vy * vy)` into a multiply-add, which the tier could neither see nor forbid. The C builds run the pass at 0.83 to 0.96 of the built-in cost (a different compiler's loop over the same operations).
- Hypothesis 5 holds: the importer answers the 16 expected bytes with the content hash `0x6ff0a205887272cc` in all five samples, each spawn plus round trip taking 1.4 to 2.0 ms, three orders of magnitude above a chunk.
- Beyond the hypotheses: the whole measurement (the reference, four builds, thirty runs of 1 000 ticks, four reloads, five round trips) takes 20 seconds on this machine; the first `rustup target add wasm32-unknown-unknown` of a machine is the one network-dependent step.

The research CI run on the five cells follows; the raw measurements and the environment of each cell will be the artifacts of that run.
