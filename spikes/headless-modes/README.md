# Headless modes

Throwaway spike of the headless execution research. It runs the [reference workload](../reference-workload/README.md) under the headless and harness hosts of the [runtime skeleton](../runtime-skeleton/README.md) spike and measures, instead of assuming, what "headless" means for such a host: whether it runs in a minimal Linux container with no windowing, graphics or audio library and gives the reference hashes; whether the binary built without the presentation capability imports any windowing, graphics or audio library of its platform, read from the binary's own dynamic imports; whether the same binary runs from a non-interactive context with no session of any kind; how many worlds one machine steps at once, the first measured number of worlds per machine for this workload; and whether a capability that is not built, discovered absent or requested absent describes the host one and the same way.

## Layout

- `src/world.rs`: a trimmed copy of the runtime skeleton spike's core: the reference workload stepped on the dependency-counting tick graph (the hash of a tick overlaps the next tick's passes on the other buffer), stepped by whole ticks, with the extraction extension point a capability implements. No snapshot and no injection: this spike needs neither.
- `src/imports.rs`: the dynamic imports of an executable read from the file, in the three formats of the boundary: ELF64 (the `DT_NEEDED` entries of the dynamic section), Mach-O 64 (the dylib load commands) and PE32+ (the import and delay-load directories), and the list of windowing, graphics and audio libraries per format that the imports are matched against.
- `src/session.rs`: the facts of a process's environment (display and session variables, device nodes, container markers and the system's windowing, graphics and audio libraries on Linux; session variables on macOS; session variables and the console window on Windows), the discovery of a display or window server session by the presentation capability, and the host's self-description: four capability axes (presentation, audio output, input devices, platform session), each with a form, no reason inside.
- `src/main.rs`: the scenarios and the report. The `presentation` feature of the crate is the capability's presence at build time: with it, the binary registers the skeleton spike's stub extraction node when the capability was discovered and not requested absent, and links one platform windowing library for the discovery (`libX11.so.6` on Linux, CoreGraphics on macOS, `user32.dll` on Windows), which is the positive control of the import check. Without it the capability does not exist in the binary. `--headless` requests the headless mode: every axis null whatever discovery finds. `--child-hosts` runs the hosts at one worker and prints their report with the child's own session facts; `--describe` prints the self-description and what discovery found.

## Hypotheses

With the reference workload, version 1, default size (10 000 entities, 1 000 ticks), wander system off, compiled by one pinned Rust toolchain at default target features:

1. The headless host (1 000 ticks back to back) and the harness host (1 000 ticks in batches of ten with a 1 ms pause after every batch) run in a minimal Linux container (the `rust:1.99.1-slim-bookworm` image: no X11, Wayland, GPU or audio library installed, no display variable, started as a container job on the two Linux cells) and give the reference hashes, at 1 and 4 workers.
2. On every cell, the binary built without the capability imports no windowing, graphics or audio library of its platform, read from its own dynamic imports (the ELF dynamic section on Linux, the load commands on macOS, the import table on Windows); the binary built with the capability imports exactly the one library it links for discovery. This is the static form of "no GPU and no audio device" that the runners' interactive sessions cannot show dynamically.
3. On Windows and macOS, the same binary runs from a non-interactive context the runner offers (a detached child process with no console and an environment reduced to the loader's variables on Windows; a child process with an empty environment on macOS and Linux), sees no session variable of any kind, and gives the reference hashes. The true headless sessions (a Windows service session, a macOS process over a remote shell with no window server session) are not reproducible on hosted runners; they are validated by hand with the same binary, whose session facts and hashes say what they saw.
4. N worlds, each at one worker on its own thread, started together, reach N times the single-world throughput within 15 percent on dedicated cores, each world reproducing the reference hashes of its own seed, for N of 1, 2 and 4 on the cells (and the cell's CPU count when different) and up to 10 on the founder's machine; for contrast, one world at N workers measures intra-world parallelism on the same machine.
5. Three absences describe the host identically: a capability not built (the binary without the feature), a capability discovered absent (the binary with the feature on a machine with no display: the Linux cells) and a capability requested absent (the binary with the feature started with `--headless` on a machine that has a display or window server session: the founder's machine, the macOS and Windows runners). The description carries the forms of the four axes and no reason; what discovery found is reported beside it.

## Method

The binary the research CI builds and runs is the configuration without the capability. It runs both hosts at 1 and 4 workers (and the machine's CPU count when different), each compared tick by tick with the sequential reference; reads its own imports; builds the other configuration as a child `cargo build` into a temporary target directory (in the container the link of `libX11.so.6` is expected to fail, and that failure is a fact of the report, not an error of the spike), reads that binary's imports, runs it with `--describe` and `--describe --headless`, and runs its hosts at one worker through `--child-hosts`; compares the three descriptions as strings; runs itself as the non-interactive child described in hypothesis 3; and steps N worlds on N threads, then one world at N workers, for the N values of hypothesis 4, computing the reference of every seed once (the reference runs also give the sequential implementation's ticks per second). The session facts of every process (the binary, the other configuration, the non-interactive child) are in the report beside their hashes.

The self-checks (`cargo test -p headless-modes`, and with `--features presentation`) verify on the small size that the hosts reproduce the reference hashes at 1, 2 and 3 workers, that three worlds on three threads each reproduce their own reference, that the extraction node runs at every fixed point and changes nothing, that the import parser reads the test binary and finds no windowing, graphics or audio library in the build without the feature and exactly the positive control in the build with it, that the matcher ignores case, that unreadable and fat files are refused with a reason, that the three absences describe themselves identically and a present capability differently, and that the whole report runs with every world matching and the non-interactive child seeing no session variable.

## Environment

Research CI, workflow `research-ci.yml`, five cells (see [`spikes/README.md`](../README.md)), run on demand with `-f spike=headless-modes`; plus the two Linux cells inside the `rust:1.99.1-slim-bookworm` container (Debian 12, glibc 2.36, the pinned toolchain preinstalled, no windowing, graphics or audio library), run on demand through the workflow's container input. Rust toolchain pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), release profile, default target features of each target; plus a local run on an Apple M5 (10 cores, macOS 26) outside the matrix. The x86_64 runners' 4 virtual CPUs are two cores with hyperthreads and the macOS runner has 3, which the ratios of hypothesis 4 must be read against; the founder's machine has four performance cores and six efficiency cores. Timings from hosted runners compare per processor only.

## Result

Research CI [run](https://github.com/ludenea/ludenea/actions/runs/41708442487) of 2026-11-03 on the five cells (AMD EPYC 9V74 on both x86_64 cells that day, Neoverse N2 on Linux ARM64, Cobalt 100 on Windows ARM64, a virtual Apple M1 with 3 CPUs on macOS) and on the two Linux cells inside the `rust:1.99.1-slim-bookworm` container (Debian 12, glibc 2.36; the x86_64 container cell landed on an AMD EPYC 7763), plus a local run the same day on an Apple M5 (10 cores, macOS 26) outside the matrix. Every world of every scenario reproduces the sequential reference on every cell: the two hosts at 1 and 4 workers (3 as well on macOS, 10 locally), the configuration with the capability at one worker where it built, the non-interactive child, and every world of the many-worlds runs. - Hypothesis 1 holds: inside the container, on both Linux cells, the headless host and the harness host give the reference hashes at 1 and 4 workers, in a process with no display variable, no entry under `/dev/dri` or `/dev/snd`, none of the seven windowing, graphics and audio libraries the spike looks for in `ldconfig -p`, and the container markers present. On the ARM64 pair, which landed on the same processor model, the container costs nothing measurable (741 against 737 ticks per second at 1 worker, 2 591 against 2 585 at 4); the x86_64 pair landed on two processor models, so its difference is the processors'. The configuration with the capability does not even link in the container (`libX11.so.6` is not in the image), the recorded form of "a windowed build needs what the headless image lacks".
- Hypothesis 2 holds on every cell: the binary without the capability imports `libgcc_s.so.1`, `libm.so.6` and `libc.so.6` on Linux (plus the loader on x86_64), `/usr/lib/libSystem.B.dylib` alone on macOS, and `KERNEL32.dll`, `ntdll.dll`, `api-ms-win-core-synch-l1-2-0.dll`, `VCRUNTIME140.dll` and six `api-ms-win-crt-*` sets on Windows, none of them a windowing, graphics or audio library; the binary with the capability adds exactly its positive control (`libX11.so.6`; CoreGraphics with the CoreFoundation it pulls in; `USER32.dll`), which the check flags.
- Hypothesis 3 holds in the form the runners offer: the detached child without a console and with the loader's variables only on Windows (no `SESSIONNAME`, `USERNAME` or `USERPROFILE` seen, console window null), and the child with an empty environment on macOS and Linux (no display, session or XPC variable seen), run both hosts to the reference hashes on every cell. Two facts about the runners' own sessions: the Windows runner's process has no console window and no `SESSIONNAME` variable while its window station is interactive (`GetUserObjectInformationW` reports `WSF_VISIBLE`), and the macOS runner's process has no `SECURITYSESSIONID` variable while `CGSessionCopyCurrentDictionary` finds a window server session; the founder's terminal has the variable. Environment variables are therefore not a proxy for a session; the platform calls are, and a capability's discovery must use them. The true headless sessions (a Windows service session, a macOS process over a remote shell) remain to validate by hand with this binary.
- Hypothesis 4 holds within 15 percent where the virtual CPUs are cores: on the two ARM64 cells and their container counterpart, 2 and 4 worlds at one worker each reach 0.98 to 1.00 of N times the single world (2 872 to 2 949 ticks per second for 4 worlds); on the x86_64 cells 2 worlds reach 0.93 to 1.00 and 4 worlds 0.67 to 0.75 (the 4 virtual CPUs are two cores with hyperthreads); on the macOS runner's 3 virtual CPUs 2 and 3 worlds reach 0.84 and 0.80; on the founder's machine 2 and 4 worlds reach 0.98 and 0.95 (3 785 ticks per second), and 6, 8 and 10 worlds 0.82, 0.74 and 0.63 (6 213 ticks per second for 10 worlds, the efficiency cores being slower than the performance cores the single world ran on). World-level parallelism beats intra-world parallelism everywhere but on the macOS runner: 4 worlds at one worker give 2 931 to 2 949 ticks per second against 2 538 to 2 584 for one world at 4 workers on Linux ARM64, 2 872 against 1 973 on Windows ARM64, 1 307 to 1 558 against 1 059 to 1 434 on x86_64, and 6 213 against 4 029 at 10 locally; on the macOS runner one world at 2 and 3 workers (1 167 and 1 675) beats 2 and 3 worlds (1 007 and 1 447). The first measured number of worlds per machine for this workload: four worlds at about 735 ticks per second each on a 4-core ARM64 runner, ten at about 660 on the founder's machine.
- Hypothesis 5 holds wherever the comparison exists: the capability not built, the capability discovered absent (the Linux cells, where `XOpenDisplay` finds no display) and the capability requested absent (the macOS and Windows runners and the founder's machine, where discovery finds a window server session or an interactive window station) describe the host with the one string `{"presentation":"null","audio_output":"null","input_devices":"null","platform_session":"none"}`, while the discovered description on a machine with a session reads `windowed` and `interactive`. In the container the comparison is unavailable by construction, since the capability's configuration does not build there.
- Beyond the hypotheses: the harness host's hundred 1 ms pauses last 104 to 126 ms on every machine but the macOS runner, where they last 406 to 476 ms (the sleep fact of the skeleton spike again); the sequential reference implementation runs at 440 to 754 ticks per second on the cells (502 in the x86_64 container, on its faster processor) and 990 locally.

The raw measurements and the environment of each cell are the artifacts of the run. The result holds for the reference workload version 1 at this toolchain and on these images.
